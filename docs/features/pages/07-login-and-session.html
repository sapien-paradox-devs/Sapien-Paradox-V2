Login And Session

A cookie on the parent domain, rehydrated on boot, and the failure that localhost can never show you.

IdentityD6D7D30D62built

Why it exists

V1 shipped without session persistence and filed it as a future note: a refresh signed you out. V2 boots by asking GET /api/auth/me and rehydrating from the answer, which is also why the root machine starts in checking rather than assuming anonymous — a token link opened on a cold phone must never be bounced to /login by a pending auth check.

The structural decision underneath is that there are exactly two ways to be recognised, and no endpoint accepts both. A session cookie is ambient authority: the browser attaches it to any request to our origin, including one a third-party page provoked. A grant token is not — it has to be in the URL. So CSRF is enforced on one lane and off on the other, and neither file has to decide which identity wins.

Two lanes, never crossed

What each part does

01
core/api/auth.py · POST /auth/login
Email and password for a session cookie. The same 401 for a bad password and an unknown email — distinguishing them makes an account-enumeration oracle, and a reader who mistyped either is helped by neither. Login rotates the CSRF token, so the new one is handed back in a header.
02
core/api/auth.py · GET /auth/me · POST /auth/logout
me is what the SPA boots from, and where a reload gets its CSRF token back; it answers 401 when anonymous, which is exactly what the root machine expects. logout clears the session.
03
core/auth/__init__.py
The three auth classes. SessionAuth checks CSRF itself on unsafe methods; StaffAuth extends it with the staff test; GrantAuth reads the token off the path — or, for POST /api/chat, out of the JSON body — and resolves it to a grant.
04
config/settings.py · the cookie block
COOKIE_DOMAIN scopes the session cookie to the parent domain so both origins share it; SameSite is env-driven and None while the two hosts are unrelated; CORS allows credentials and exposes X-CSRFToken.
05
pages/machine/machine.ts · the session region
checking → authenticated | anonymous, plus loggingOut, which clears the local session either way so a failed logout call cannot strand someone in an authenticated-looking UI. Signing in while signed in is allowed: that is a reader switching to their staff account.
06
pages/machine/sync.ts
URL → machine, and the only sender of ROUTE. Navigation is unidirectional: a page asks for a URL, the URL is pushed, and the change arrives back here — so there is no machine-to-URL loop to guard. It is also where the page transition starts.
07
pages/login/machine/machine.ts
idle → submitting, and a second path: linkForm → sendingLink → linkSent, for a reader who has never had a password. Only the outcome travels up, as AUTHENTICATED; the form's own lifecycle never reaches the root.
08
pages/admin-login/
The staff door, its own page at /admin/login (D82), matched before isAdminPath in the route table so it is not swallowed by the admin.
09
pages/BootSkeleton.tsx
What shows while checking is in flight. A skeleton rather than the word "Loading", because the first frame after a tap should look like the page that is arriving.
D62 — the machine that was retired

There was going to be a dedicated auth machine. There isn't: the session is a region of the root machine and the form is the login page's own machine, which is where those states belong. The decision records the removal rather than leaving a third home for the same question.

Gotchas

  • CSRF had never actually been enforced. Ninja checks it only for its own cookie auth classes, and SessionAuth is a plain callable — so it got no check at all until it started asking for one explicitly. Every session endpoint depended on a protection that was not running.
  • Sign-in appeared to hang. ROUTE was handled on the root, so every navigation re-entered the parallel machine, dropped the AUTHENTICATED event reported meanwhile, and sent the session back to checking. Moving the handler onto the page region fixed it.
  • The SPA cannot read the API's CSRF cookie across unrelated hosts. Hence the header hand-over on login and on /me, the CORS exposure, and the in-memory copy in fetcher.ts. When both sit under one parent domain the cookie becomes readable and the same code still works.
  • Staff who are not staff get a 401, not a 403. Ninja's auth classes have no "authenticated but not allowed", and the admin screens only run for staff, so the distinction would help nobody.
  • Admin sign-in had to accept a username. The first staff account was created with createsuperuser, which asks for a username — and the form demanded an email, so the owner could not get in.
  • Safari is still unverified. DESIGN.md calls the cross-subdomain cookie the most likely quiet failure in the product, ITP is what would break it, and localhost can never reveal it. It is the one open item on this feature.
