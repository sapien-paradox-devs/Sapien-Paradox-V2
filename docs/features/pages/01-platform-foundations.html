Platform Foundations

One repo, two deployable apps, nine shared values, and a clone that runs with zero credentials.

FoundationsD5D6D20D23D34D35D66built

Why it exists

V1 was two repositories split by lane — services and UI. Every feature that touched both sides had to be split in half, with the merge order managed by hand, and the two halves drifted. Five of V2's twelve planned slices touch both sides in one change, so V2 is one repository with one git history and one PR per slice (D6).

The second rule is harder and pays more: a fresh clone runs with zero credentials. Every external system reads env and falls back to something local — the database to SQLite, storage to the filesystem, WhatsApp to printing on screen, the companion to unavailable. That is why CI needs no secrets, and why a new machine is productive in one command.

The shape

What each part does

01
shared/constants.json
The nine values where a mismatch between the two sides is a bug: the three pace keys and the five route patterns. Nothing that only one side uses is allowed in here (D20).
02
apps/api/core/constants.py
Reads that file at import, not lazily, so a malformed constants file fails at startup rather than on the first reader's request. Exports PACE_KEYS, PACE_CHOICES and ROUTES — the database stores neutral keys, and the poetic labels live in labels.ts.
03
apps/web/src/lib/constants.ts
Re-exports the same file with real types, and runs assertPaceInSync at module load. D20 assumed as const would keep the literal union on a JSON import; it doesn't, so the union is declared here and checked against the JSON at boot.
04
apps/api/config/settings.py
One env-driven file, and the only place a default lives. Chooses the database (DATABASE_URL or SQLite), the storage backend (R2, in-memory under test, filesystem otherwise), the WhatsApp backend, the cookie policy, and every window and cap: GRANT_TTL_DAYS, PACE_DELAY_DAYS_*, the three cooldowns, the upload limits.
05
apps/api/config/logging.py · urls.py · wsgi.py
Logging is stdout only, at LOG_LEVEL, for the host's own viewer — no log vendor (D22). urls.py mounts the single Ninja API under /api and Django admin under /django-admin.
06
apps/api/core/api/__init__.py
The NinjaAPI instance and the twelve routers. This package is HTTP only: schemas in, schemas out. A module in here that queries the ORM to make a decision is in the wrong layer.
07
apps/web/src/lib/env.ts
The one place that knows the API's address. Empty in development, where Vite proxies /api to localhost:8000; absolute in production from VITE_API_BASE.
08
apps/web/src/lib/fetcher.ts
The only way the app talks to the API. Owns the base URL, credentials: "include" on every request, the X-CSRFToken header on every unsafe one, and one error shape carrying status — so a machine guard is a single line. Also blob() for page images and send(), a keepalive POST for the last word of a reading session.
09
apps/web/src/lib/labels.ts
Every string the reader sees, in twenty sections keyed by surface. Mandate 1: zero hardcoded strings in components.
10
render.yaml
Provisions the database, the web service, the cadence cron and the shared env group from one file. Migrations and render_chapters run in the start command, not pre-deploy, because pre-deploy is a paid feature.
11
.github/workflows/api.yml · web.yml
Two path-filtered workflows. API: check, makemigrations --check, test core. Web: npm test, npm run build. Neither is given a credential — that is the proof the fallbacks are real.

The deploy rule the bucket depends on

Nothing in this codebase generates a permanent storage URL — page images and covers are streamed through the API. A public bucket would bypass grant tokens and expiry at the infrastructure layer while every line of application code still looked correct. The bucket must stay private.

Gotchas

  • The first deploy 400s on a hostname nobody could know. Render's health check arrives with <service>.onrender.com as the Host header, before anyone has typed it into the dashboard. settings.py appends RENDER_EXTERNAL_HOSTNAME to ALLOWED_HOSTS rather than assigning it, so the check passes and an explicit api.<domain> keeps working.
  • A SameSite=None cookie without Secure is dropped silently. Login appears to succeed and every later request is anonymous. Settings now refuse to start in that combination instead of letting it fail quietly.
  • Both cookies have to be None, not just the session one. While the app is on vercel.app and the API on onrender.com they are unrelated sites; set only SESSION_COOKIE_SAMESITE and every write is refused as csrf_failed. Back to Lax once the real domain is pointed.
  • The SPA cannot read the API's CSRF cookie across unrelated sites. So the token travels in an X-CSRFToken response header, which CORS must expose, and fetcher.ts keeps it in memory. The cookie is only the fallback.
  • Vite inlines env vars at build time. A production build with VITE_API_BASE unset would call its own origin and 404 every request, so env.ts carries a temporary production fallback. It is a second place that knows the API address — the thing D6 exists to prevent — and it gets deleted when the domain lands.
  • Free Postgres expires thirty days after creation, with no backups. D35 time-boxed the free tier and that clock is real: both plans go paid before the first WhatsApp link reaches a real reader. The free web service also sleeps, so a cold tap waits about a minute.
  • A service-level env var beats the shared group. The live web service predates the group, so syncing render.yaml creates the group but does not remove the older values. Copy them in — the secret key included, or everyone gets signed out — then delete them from the service.
