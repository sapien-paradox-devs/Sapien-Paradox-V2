Credentials And Recovery

No email provider, so a password is set and recovered over WhatsApp — single-use, cooled down, and mute about who exists.

IdentityD16D21D31built

Why it exists

There is no email provider, on purpose (D16). WhatsApp is the only outbound channel, so it is also the recovery channel — and that single fact shapes everything here. A reset link sits in a chat history forever, which makes a reusable one a permanent account key. So the token is single-use, and used_at is stamped in the same step as the password change.

The other reason this exists is a hole a paying reader falls into. D26 gives a new reader an unusable password, so the login form can never admit them; their only key is a link that expires in an hour. Without a way to ask for a fresh one, a reader who opened WhatsApp a day late had no route into the product they had paid for.

One answer, whatever happened

What each part does

01
core/services/onboarding.py · the first token
A new reader gets an unusable password and, if they have a phone, a PasswordResetToken minted inside the same transaction as their order — then a set-a-password message after commit. This is the ordinary way a reader first gains a password.
02
core/api/reset.py · POST /auth/reset/request
Normalises the phone, finds the user, checks for a token row created inside the cooldown window, and either mints one and sends it or does nothing. Returns {"status": "ok"} in every case.
03
core/api/reset.py · POST /auth/reset/confirm
Rejects unknown, expired and already-used tokens with one 410, enforces a minimum password length, sets the password and stamps used_at.
04
core/services/phone.py
One spelling of a number, everywhere. Without it a reader typing their own number in a different shape would get the same reassuring answer and no message — the failure this endpoint's own design hides best.
05
core/services/whatsapp.py · send_password_reset
One of the named wrappers over the single delivery mechanism. It builds the template's variables and nothing else; retry, logging and the backend switch belong to _deliver.
06
pages/login/ · the link form
The second path through the login page: a reader who cannot sign in asks for a fresh link by phone number, and the page says a link is on its way — with the same wording regardless of whether the number was known.
07
pages/reset/
The page the link lands on, at /reset/:token. It sets the password, reports link_expired as a normal state with a way to ask for a new link, and signs the reader in on success.
08
core/api/profile.py · POST /auth/password
Changing a password from inside the app. It requires the current one only from a reader who has a usable password — a reader who arrived by link and never set one has nothing to type — and refreshes the session hash so they are not signed out of their own session.
09
core/api/checkout.py · POST /checkout/resend
The other way a set-password link is re-sent: from the welcome page, authorised by the Razorpay order id, and only when the reader still has no usable password.

The windows

RESET_TOKEN_TTL_MINUTES60How long a set-a-password link stays usable.

Gotchas

  • An unusable password is not a blank password. It is why the login form can never admit a brand-new paying reader, and why the link form beside it is not a convenience — it is their only door.
  • The cooldown is per account, so it can be occupied by a stranger. Anyone who knows a reader's number can trigger one message and hold the window for fifteen minutes. The alternative — counting per requester — needs an identity the endpoint deliberately does not have, and the cost of this shape is one unwanted message rather than an account-enumeration oracle.
  • Normalisation has to happen before the lookup, not after. Both endpoints answer the same way whether or not a user was found, so a formatting mismatch produces a perfectly reassuring silence.
  • used_at and the password change are one step. Stamping it later, or in a second request, leaves a window in which the link in WhatsApp still works.
  • The reset token is a separate table, not a grant with a purpose column. A grant is multi-open and lives seven days; this is single-use and lives an hour. One table would have accumulated if purpose == branches and served neither well.
  • Nothing here logs a token. Log lines carry the user's primary key instead — D22's rule, and the reason these endpoints are quiet about what they did.
