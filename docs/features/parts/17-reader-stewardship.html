Why it exists

D75 said the admin would be an upgraded Django admin. D82 replaced that: the admin lives in the app at /admin, with its own sign-in page, because the owner's work — find a reader, fix a typo, send a chapter again, take someone off the list — is a product surface, not a database browser.

The rule that keeps it honest is that adding a reader goes through the acquisition machine, exactly like a payment. The four identity cases of D26 apply to an admin typing a name as much as to Razorpay's webhook, so there is no second, looser way for a reader to come into existence.

Removing is not deleting

What each part does

01
core/auth/__init__.py · StaffAuth
A session, and the account is staff. CSRF is checked first, by SessionAuth — a staff session is the most valuable ambient authority the product has.
02
core/selectors.py · readers · reader · orders_of · is_erased
Every read the admin needs: the list with a book count per reader, search across name, email and phone, a status filter, and the books one reader owns. Staff accounts are included, because an owner who is also a reader should be findable.
03
core/api/admin.py · list · detail
Two reads, capped at 200 rows, mapping selectors to typed schemas. No ORM calls of its own.
04
core/api/admin.py · POST /admin/readers
Builds a PurchaseAttempt and dispatches PAID to the acquisition machine with the same deps checkout uses. A refusal comes back as a 409 with the code and the form field it belongs to, so the screen can put the message where the admin is looking.
05
core/services/onboarding.py · update_reader
Name, email or phone, each refused on a clash with another reader. The phone is normalised first, for the same reason as at signup: two spellings of one number would otherwise be two accounts.
06
core/services/onboarding.py · deactivate · reactivate
Reversible removal. Reactivating an erased reader is refused — there is nothing left to restore.
07
core/services/onboarding.py · erase_reader
Placeholders that still satisfy the unique constraints, an unusable password, MessageLog.to_phone blanked, unused reset tokens spent so none can be redeemed — and the orders left standing.
08
pages/admin-login/ · pages/admin/useAdminPath.ts
The staff door and the admin's own internal routing, kept out of the root machine: the root knows only that admin and adminLogin are pages.
09
pages/admin/readers/ · reader/ · reader-new/
The list with search and status filter, one reader's detail with their books and the four actions, and the add-a-reader form — each its own machine, each mapping a 409's field onto the input it belongs to.
10
pages/admin/refusal.ts
One place that turns a refusal code into a sentence, so the same code reads the same way on every admin screen.

Gotchas

  • An admin cannot create a reader more loosely than a payment can. Routing the form through the acquisition machine is what guarantees it, and it is why the admin gets the same "these two fields name two different readers" refusal that a webhook does.
  • Erased placeholders must still satisfy unique constraints. Hence erased-<pk>@erased.invalid and a synthetic phone: blanking the fields outright would collide the moment a second reader was erased.
  • Erasure has to spend unused reset tokens. Otherwise a link already in WhatsApp could still set a password on the emptied account.
  • The audit row stores no old values. That is not an oversight — recording what was erased would mean it had not been erased.
  • Deactivation is checked in the access seam, not at login. Checking it at sign-in would leave every WhatsApp link the reader holds working perfectly.
  • Django admin is still mounted. /django-admin remains for the eight model screens and the resend action, so nothing was lost while the in-app admin was built — but two admins mean two places a change can be made, and only one of them writes an AccountChange row.
