Why it exists

The product's main path is a tap on a WhatsApp message, usually on a phone, often inside WhatsApp's own browser with its own cookie jar. There is no session there and there never will be, so the token is the whole credential. Everything else about this feature follows from that, including the parts that look like over-engineering.

Links expire after seven days (D8), which means the week-late reader is not an edge case — they are a normal visitor, arriving on a dead link with no way to sign in. Sanctuary is the screen for them, and it has one button that sends a fresh link to the phone on the account (D9).

Two ways in, and what happens to a dead link

What each part does

01
core/services/grants.py · mint_or_reuse
The newest unexpired grant for this reader and chapter, or a new one — excluding scheduled rows, which hold tokens nobody has been sent yet. This is what makes GET /api/read/{id} honest as a GET.
02
core/services/grants.py · find vs validate
Two lookups on purpose. validate collapses expired into None, which is right for a caller that only wants a usable grant. find returns the row either way, because the API layer needs to tell "this link has rested" from "no such link".
03
core/services/grants.py · reissue
Creates a new row rather than extending expires_at. Extending would silently revive every forwarded copy of the old link — and (user, chapter) is deliberately non-unique so that this is possible.
04
core/auth/__init__.py · GrantAuth
Reads the token out of the path — or, for the chat endpoint, out of the JSON body — and returns the grant, so the endpoint reaches the reader and the chapter without a second query. It does not judge expiry.
05
core/api/grants.py · _dispatch_or_refuse
The one place refusal codes become HTTP: expired → 410, not_owner → 403, no_video → 404. No layer below knows what a status code is.
06
core/api/grants.py · GET /api/grants/{token}
What the chamber needs to render: book title, chapter number and title, the reader's place, whether it is complete, whether there is a video — and firstOpen, read before OPEN stamps opened_at, so the ceremony can play exactly once.
07
core/api/read.py · GET /api/read/{chapter_id}
Exchanges a chapter for a token and redirects. A GET, and idempotent: making it a POST would put an interstitial screen on the one path that should never have one.
08
core/api/read.py · POST /chapters/{id}/send · /reissue
Send-to-my-WhatsApp from Home, cooled down and reusing the live grant; and sanctuary's tap, which works on an expired token and sends to the owner's phone. Both answer 429 when a message went out recently.
09
pages/opening/machine/machine.ts
The invisible page behind /read/:chapterId: it starts in waiting, moves on SESSION_SETTLED, swaps the chapter for a token and redirects.
10
pages/reader/Sanctuary.tsx
The screen for a rested link: no alarm, one tap, and the reissue region of the reader machine keeps the request in flight without blanking what the reader is looking at.

Gotchas

  • waiting prevents a bug that only appears on reload. On a hard refresh the session region is still checking, and treating "not yet authenticated" as "anonymous" bounces a signed-in reader to /login — invisible in development, where the session check resolves instantly.
  • 410, not 404, for an expired token. The status is what tells the chamber to show sanctuary, which has a button, rather than the dead end an unowned chapter gets. Collapsing the two would make the recovery path unreachable.
  • Expiry must not be checked during authentication. It would turn a rested link into a 401 beside tokens that were never real, and the distinction the product needs would be gone before any endpoint saw it.
  • A live token is never sufficient on its own. Ownership is re-checked on every grant request, so a refund or a deactivation takes effect on the next tap rather than whenever the token happens to lapse.
  • firstOpen has to be read before dispatching. OPEN stamps opened_at, so asking afterwards always answers "no" and the ceremony never plays.
  • Re-issue sends to the account's phone, never to whoever tapped. That is what makes the endpoint safe to expose on an expired token: a stranger holding a forwarded link can cause the owner to receive a message, and can receive nothing themselves.
  • Home mints no tokens in its payload. Five credentials in a response that gets cached, logged and screenshotted would undo expiry entirely — so the link is minted when the reader asks for one.
