Why it exists

WhatsApp is the product's only outbound channel: chapters, recovery links and password links all arrive there, and there is no email provider to fall back on (D16). D27 therefore insisted on one mechanism with named wrappers rather than a function per message type. A second implementation would mean a second retry policy, and duplicated retry rules drift — one copy gets the never-retry-a-4xx rule and the other does not, and you find out when a bad number has been retried for a year.

The other structural rule: delivery returns, it never raises. A function that cannot raise cannot break a caller's transaction, which makes the "reader survives a Twilio hiccup" guarantee structural instead of something five callers each have to remember.

One send, from wrapper to provider

What each part does

01
core/content/templates.py
The four templates as data: key, the Meta-registered provider_name, the ordered variable names, and a plain-text body. Positional variables mean order is part of the contract. render() raises on a missing variable, because that is a programmer error rather than a delivery failure.
02
core/services/whatsapp.py · the wrappers
send_chapter, send_fresh_link, send_password_reset. Each builds one template's values and calls the shared mechanism. send_fresh_link is a separate template from send_chapter even though the variables match — a reader who asked for a fresh link should not be told their chapter is "ready when you are" as though nothing had happened.
03
core/services/whatsapp.py · reader_link / reset_link
Links built from APP_BASE_URL and the route patterns in shared/constants.json — the same file the SPA routes from, because drift here 404s every link in every message ever sent.
04
core/services/whatsapp.py · _deliver
Renders, writes the MessageLog as pending before the first attempt so a crash leaves evidence, then loops: attempt, dispatch ATTEMPT, read the row's new status, sleep, repeat. No queue — the retry is inside the request, about two seconds at worst.
05
core/machines/delivery/machine.py
Three rows: accepted → sent; transient and under the cap → stay pending and count the attempt; anything else → failed. This is the entire retry policy, and having it in one table is what makes a second copy impossible.
06
core/services/whatsapp.py · _twilio_send
Real delivery. Twilio's HTTP status decides retryability, not the message text: 429 and 5xx raise TransientDeliveryError, every other 4xx raises PermanentDeliveryError, and a connection-level exception with no status is treated as transient.
07
core/services/whatsapp.py · _console_send
The no-credentials fallback: prints the message in the developer's own terminal and returns the sentinel provider id console. In a non-debug deployment it also logs an error, because every "sent" it records is a message that never existed.
08
core/services/whatsapp.py · left_the_building
The question a caller must ask before telling a reader anything: status sent and the provider id is not the console sentinel. The console backend accepts everything — that is its job.
09
core/services/whatsapp.py · recently_sent
The cooldown, counted from MessageLog rows rather than a counter, because the rows are written anyway and a counter is a second truth. Two callers need it: the signed-in resend, and the post-checkout one, which has no session.
10
core/management/commands/send_chapter.py · admin action
Both go through the same seam, so a resend from the admin list and a resend from a terminal produce the same rows and obey the same retry policy.

Why all four were written before three were needed

Every cadence message is business-initiated, so it falls outside WhatsApp's 24-hour window and must use a template Meta has already approved. Approval takes days to weeks, and an approved unused template costs nothing — so submitting the reminder now keeps it off the critical path later. Until the sender application and the templates clear, the whole product runs on the console backend.

Gotchas

  • sent does not mean delivered, and on a credential-less deployment it does not even mean sent. The console backend accepts everything, so every message reads as sent while nothing left the building. Any caller that reports delivery to a reader has to ask left_the_building instead — and the welcome page learned this the hard way by asserting a delivery that had never happened.
  • The rendered body is never stored or logged. It contains a live token, which is a credential, and logs are less protected than the database. template_key plus the grant reproduces it exactly.
  • A missing template variable must raise, not fail. A failed row would blame Twilio for a bug in our own call site.
  • A number stored without its + is rejected by Twilio. Hence one normalisation function, applied on the way in and again when building the whatsapp: address.
  • The retry cap had drifted while nothing called the machine. The table and the loop disagreed about how many attempts were allowed, and nobody noticed until the machine was wired to the code that actually sends — the strongest argument in the repo for wiring a machine as soon as you write it.
  • Permanent failures must not be retried. Retrying an invalid number is pure delay: it cannot succeed, and it spends the request's remaining budget before reporting the same thing.
  • Nothing surfaces a failed send. The row is in MessageLog and no screen shows it, so a reader whose chapter never arrived looks, from the outside, exactly like a reader who has not opened it.
