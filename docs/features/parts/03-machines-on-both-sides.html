Why it exists

In V1 the flow was wherever it had been written: an if in an endpoint, a raise in a service, a useState in a component. Nobody could answer "what can happen to a grant?" without reading everything. D36 makes the answer a file: a machine is a list of states and a transition table, and the table is plain data.

The rule on both sides is the same. Any act on a subject that has a machine is an event dispatched to that machine. Guards decide, actions call services through ctx.deps, and the endpoint only maps the result to a status code. An endpoint never performs a flow step itself, and never dispatches one event to borrow its checks for another.

One dispatch, end to end

What each part does — the server

01
core/machines/__init__.py
The whole framework, in one file: Spec (name, initial, states, transitions — pure data), Ctx (deps, payload, and refuse() / produce()), TransitionResult (ok, state, refusal, data), and dispatch. Also the two adapters that let a guard and an action be written with the same signature.
02
core/machines/binding.py
The only Django-aware module in the layer. dispatch_model saves the subject when a transition succeeds; save_state writes the state column plus whatever touched() marked, so one transition cannot clobber a column another instance changed.
03
core/machines/<name>/machine.py
The transition table, and nothing else. Each row is a trigger, a source, a destination, its conditions and its actions, with the reason for the row in a comment above it. dest: None is an internal transition — it runs its action without moving, which is what every refusal wants.
04
core/machines/<name>/guards.py
Predicates over the subject and ctx. They read; they never write. owns_book asks the access seam, so ownership has exactly one definition in the codebase.
05
core/machines/<name>/actions.py
Effects, each through ctx.deps: stamp a timestamp, send a chapter, record progress, mint a fresh grant, sign a video URL — or record a refusal code with ctx.refuse("expired").
06
core/machines/registry.py · diagram.py
Every machine in one list, for the tools that must enumerate them. manage.py machine_diagram generates Mermaid straight from the tables, so the picture cannot drift from the code.

The row order is the logic

The reading machine's OPEN rows read: live and owned → open it; already opened → idempotent, don't restamp; past expiry → refuse expired; anything else → refuse not_owner. Move the expiry row below the catch-all and a dead link starts reporting "not yours", which sends the reader to the wrong screen. The auth-and-onboarding table caught exactly this bug during the build.

What each part does — the browser

Eighteen machines: one root, fifteen pages, two components. Each is a directory with the same five files plus types.ts, in the same order, with no exceptions and never a seventh file.

FileHolds
types.tsContext and the event union. Nothing else imports a shape from a sibling.
machine.tsDeclarative config only — states, transitions, guard and action names.
actions.tsPlain functions. assign is applied in index.ts, not here.
actors.tsfromPromise actors calling mappedFetcher. Omitted when a machine has no async work.
guards.tsNamed exports, imported as import * as guards.
index.tsComposition: setup() wires the three sibling files into the config.

Gotchas

  • ROUTE belongs to the page region, not the root. Handled on the root, every route change re-entered the whole parallel machine: the session fell back to checking, a sign-in reported meanwhile was dropped, and sign-in appeared to hang. Changing page must not touch the session region.
  • machine.provide() does not typecheck when implementations live in sibling files. Under XState v5, assign widens the event to EventObject while provide wants the union. The split survives by using setup() instead, which is why assign is applied in index.ts and actions.ts holds plain functions.
  • Expiry is not a state. The design review had expired as a fourth terminal state; building it showed expiry is derived from expires_at, and storing it as well would need a sweeper to keep the two agreeing.
  • The transitions library is loud. It logs every callback at INFO and every ignored trigger at WARNING — and an ignored trigger is normal here, since an event with no matching row is inert by design. Its logger is pinned to ERROR.
  • Written is not wired. For three weeks the tables existed and only the reading machine had a production caller; the same flow lived twice, once as a table and once as if/raise inside an endpoint. Wiring acquisition and delivery removed the duplicates — and the delivery table had already drifted on its retry cap, which nobody noticed while nothing called it.
  • One event, one question. Dispatching OPEN to borrow its guards before doing something else is the tempting shortcut and it is banned: the guards would pass, opened_at would be stamped, and the grant would move state as a side effect of an unrelated request.
