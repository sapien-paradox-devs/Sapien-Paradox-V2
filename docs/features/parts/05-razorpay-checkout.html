Why it exists

Paying is what creates a reader (D47), so checkout is the front door rather than a feature bolted to the side. The important consequence is what it is not allowed to do: no row is written when a purchase starts. An unpaid Order would be an entitlement, and can_read would have to start asking about payment status — exactly the complexity the seam exists to keep out of it.

The money then announces itself twice. Razorpay's webhook is the leg that survives the reader closing their laptop; the redirect is the leg the reader's own browser delivers, and the one that actually fires first. D48 accepts both and makes the second one a no-op.

Two legs, one reader

What each part does

01
pages/begin/machine/machine.ts
Five states: loading → browsing → submitting → paying → redirecting, with failed and refused beside them. refused returns to the form with everything still typed — a refusal is a normal state, not an error screen (D45).
02
pages/begin/machine/actors.ts
startCheckout creates the gateway order; payAndConfirm opens the Razorpay modal, waits for the result and calls confirm — one actor, because the modal's outcome is useless without the verification that follows it.
03
core/api/checkout.py · POST /api/checkout
Checks that payments are configured, that the book is published, that the pace is one of the three, normalises the phone, and asks the gateway for an order. Returns the order id, the public key, the amount and the book title — what the modal needs and nothing else.
04
core/services/payments.py
The only module that talks to Razorpay: configured(), create_order, verify_payment_signature, fetch_order, signature_is_valid. Unconfigured it raises rather than faking — a silent fake payment would leave a reader believing they had bought something.
05
core/api/checkout.py · _fulfil
Builds a PurchaseAttempt from the gateway entity's notes, dispatches PAID, and turns the refusal code into the shape both callers already speak. It decides nothing itself.
06
core/api/checkout.py · POST /checkout/confirm
Two ways in. With a payment id and signature it verifies the HMAC locally — no round trip. With only the order id, which is what a reloaded welcome page has, it fetches the order and checks status == "paid". Then it fulfils, and sets the password if one was typed and the reader has none.
07
core/api/checkout.py · POST /payments/webhook
Verifies the signature against the raw body before parsing anything, then handles order.paid and the legacy payment_link.paid. Any other event is acknowledged and ignored.
08
core/api/checkout.py · POST /checkout/resend
The reader's own escape hatch: send the chapter and the set-a-password link again. Authorised by the Razorpay order id, cooled down, and it will fulfil first if no order exists yet.
09
pages/welcome/machine/machine.ts
Four outcomes, four things worth saying: fulfilled, owned, pending, refused, plus failed when confirming itself broke. The first three offer RESEND; only a genuine identity refusal is a dead end.

Gotchas

  • Payment Links ran out. Razorpay's test mode caps them at thirty per account — total, not per day — so the whole flow moved to the Orders API and Standard Checkout. Same fulfilment, different gateway object, and the webhook still handles the old event type.
  • The webhook fails closed and silently when its secret is unset. signature_is_valid returns false on an empty secret, so the endpoint 400s before parsing and a paid reader gets nothing but a log line. That is precisely why D48's redirect leg exists, and why the secret is called out in the blueprint.
  • Nothing is created when checkout starts. Tempting, and wrong: an unpaid order is an entitlement, and every access question would then have to ask about payment status.
  • The resend endpoint is authorised by an order id, and that is safe for one reason. Everything it sends goes to the phone on the account, never to whoever asked. Someone holding the id can cause the owner to receive a message; they cannot receive one themselves.
  • The welcome page used to assert delivery. It had one state and told the reader their chapter was on its way — while a rejected webhook meant nothing had been created at all. Now it confirms, then says which of four things actually happened.
  • Phone is optional. A reader without one pays and reads through the web app; the WhatsApp legs are skipped rather than failed, so hasPhone travels back to the welcome page and changes what it offers.
  • A confirm that arrives twice must not set a password twice. It only sets one when the reader has no usable password, so a reload cannot overwrite a password the reader has since chosen.
