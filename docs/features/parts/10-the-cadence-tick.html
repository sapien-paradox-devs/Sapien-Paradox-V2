Why it exists

"Its chapters unlock on a schedule" is the second clause of the product's own sentence, and for the first ninety-five pull requests it was the one thing that did not exist: unlock_at was written in models.py, read by one guard, and set by nothing. Every chapter was available immediately, which made the pace a label rather than a promise.

D50 settled the shape, and it is the cheap one. The schedule is not computed on demand and not held in a queue — it is rows, minted at purchase. Every chapter of the book gets a grant with its unlock moment written on it, and a cron job every fifteen minutes asks one indexed question: which of these is due?

Minted once, fired later

What each part does

01
core/services/cadence.py · unlock_at_for()
When the chapter at a position unlocks: the anchor plus pace × position days, snapped to CADENCE_DELIVERY_HOUR in CADENCE_TIMEZONE when that anchor is set. Position 0 returns None — chapter one is delivered at purchase and has no unlock moment.
02
core/services/cadence.py · schedule(order)
Mints chapters 2…N as scheduled grants in one bulk_create. It writes rows and sends nothing, which is what makes it safe inside create_reader's transaction. Idempotent: a chapter the reader already holds a grant for is skipped.
03
core/services/cadence.py · due(now)
One query, oldest first: state=scheduled and unlock_at <= now. It is the reason TemporalGrant carries an index on exactly that pair.
04
core/services/cadence.py · tick(now)
Walks the due ids and, for each, opens its own transaction, re-selects the row select_for_update(skip_locked=True) with the state still scheduled, and dispatches UNLOCK. Returns a TickResult: due, sent, failed, refused.
05
core/services/cadence.py · _deps()
What the guards and actions get: the tick's own clock, access.owns, whatsapp.send_chapter, and grant_expiry — seven days from delivery, not from minting.
06
core/machines/reading/ · the UNLOCK rows
Two rows. Due and still owned → go live and deliver; due but the reader was deactivated, erased or refunded → send nothing and stay scheduled, so a reactivated reader picks up where the schedule has reached. Not yet due matches no row at all, which is inert by design.
07
core/management/commands/cadence_tick.py
The cron's entry point, plus --dry-run, which lists the due grants by primary key, reader and chapter — never the token or the link. Exits non-zero when a send failed so the run shows red in the dashboard; refusals are not failures.
08
render.yaml · sapien-cadence
A cron service on */15 * * * * in the same region as the database, running the same Django project from the shared env group. It never calls the web service, so the free tier's sleeping web instance delays nothing here.
09
core/services/access.py · can_read
The reader-facing half: a chapter is locked while a scheduled grant for it exists. That is the only place the lock is expressed, and it is why no endpoint had to change when cadence arrived.

The settings that shape a schedule

SettingDefaultEffect
PACE_DELAY_DAYS_SLOW / MEDIUM / FAST7 / 3 / 1Days between chapters. Env-overridable so a test deployment can shrink a book to minutes.
CADENCE_DELIVERY_HOUR8The local hour a chapter lands. Empty means "exactly at the offset", which is a deliberate, different behaviour rather than a missing value.
CADENCE_TIMEZONEAsia/KolkataWhich morning that hour belongs to.
GRANT_TTL_DAYS7How long a link lives, counted from delivery.

Gotchas

  • Expiry has to be re-stamped at unlock, not at minting. A grant minted today for a chapter due next month would be dead on arrival — seven days from delivery is what D8 actually means, so the reading machine restamps expires_at when the row goes live.
  • Two ticks must not send twice. Render already serialises runs of one cron job, but the row is re-selected under select_for_update(skip_locked=True) with the state re-checked, so a manual run alongside a scheduled one either skips the locked row or never sees it. On SQLite the lock is a no-op, which is fine locally.
  • A red cron run is for a human, not for recovery. The command exits non-zero when a send did not land, and the grant is still scheduled either way. Refused rows — a deactivated reader, a row another tick held — are the system working and are deliberately not counted as failures.
  • "Has it unlocked?" is answered by state, not by the clock. Comparing unlock_at to now in the access check would create a second clock that disagrees with the tick for up to fifteen minutes at every boundary.
  • Readers from before cadence hold no scheduled rows, so the whole feature is invisible to them and nothing needed backfilling.
  • Cron has no free tier. About a dollar a month at this schedule — the one paid line item while everything else sits on free plans.
  • Home still shows nothing about it. Locked chapters with their unlock dates are not built, so a reader can be on a schedule they cannot see. That is the reader-facing half of this feature and it is the next thing it needs.
