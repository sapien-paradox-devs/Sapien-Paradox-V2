Why it exists

core/models.py is data only. It holds no flow, no access rules and no delivery — those live in services and machines, and a model that started deciding things would give every rule two homes. What the file does carry is a set of constraints chosen so the rest of the code can stay simple: because an order is unique per reader and book, the access check is an existence query rather than a sum.

D18 named eight tables. There are ten: ReadingProgress arrived with D70 and AccountChange with D80, each recorded as an amendment rather than smuggled in. Django's own tables — sessions, permissions, admin log — are not designed here.

The ten tables

What each table is for

01
User
Email is the login. phone is unique and nullable — a reader with no phone can still pay and read, they just get no WhatsApp. NULL rather than an empty string, or the unique constraint would allow exactly one phoneless reader. No role column: Django's is_staff answers that question already.
02
Book
Title, slug, author, description, cover, price, and two videos — a public sample and an owners-only one. is_published keeps a half-built book with three of eight chapters from being assignable.
03
Chapter
The PDF itself, plus three things filled at upload: text_content (the companion's entire context), page_count, and page_layout (each page's size and rendered image). All three are written by explicit service calls, never by a signal. A chapter with a null layout cannot be opened.
04
Order
The entitlement, unique per reader and book, and the cadence anchor: chapter N unlocks at created_at + (N−1) × interval. pace lives here, so one reader can take one book slowly and another quickly. payment_reference is what makes the webhook idempotent — and it is blank-able, because an admin-created reader has no payment at all.
05
TemporalGrant
One reader's access to one chapter: a short token that fits in a WhatsApp message, an expires_at, an unlock_at, the first opened_at, and the reading machine's state — scheduled, live, opened. There is no expired state: expiry is derived from the timestamp.
06
ReadingProgress
furthest (0–1, only ever grows) and completed_at. Completion is declared by the reader, never inferred from reaching the last page. Nothing in access, delivery or cadence may read this table — a test holds that line.
07
MessageLog
What we tried to send and what happened: template key, the phone as a snapshot, status, attempts, provider id, error. Written pending before the attempt, so a crash mid-send leaves evidence. Never the rendered body — it contains a live token.
08
ChatUsage
One row per grant per day: message count and token counts as plain integers, so cost comparison survives a provider swap. It is the rate limiter's counter, since there is no Redis. It never stores message content.
09
PasswordResetToken
Single-use, about an hour. Separate from TemporalGrant because the lifecycles differ, and single use matters more here: a reset link sits in WhatsApp history forever, so a reusable one is a permanent account key.
10
AccountChange
One row per thing an admin did to a reader: created, updated, deactivated, reactivated, erased — with who did it. It stores no old values, or erasing would not erase.

The constraints, and what each one prevents

ConstraintOnWhat it prevents
one_order_per_user_per_bookOrderAn admin double-creating an order and silently doubling a reader's grants. It is also what makes can_read an existence check.
unique_chapter_index_per_bookChapterTwo chapter sevens, and therefore an ambiguous cadence schedule.
unique_progress_per_reader_chapterReadingProgressTwo places for one reader, and a race that loses whichever wrote first.
one_usage_row_per_grant_per_dayChatUsageA cap that can be walked past by inserting a second row for today.
tokenGrant, resetTwo readers sharing a link. Unique across the table, not per user.

index (user, chapter)TemporalGrantSlow mint-or-reuse. Deliberately an index and not unique — see below.

Gotchas

  • (user, chapter) on a grant is indexed and deliberately not unique. This looks wrong. If it were unique, re-issue would have to extend expires_at in place, and the old token would stay valid — quietly reviving access for anyone holding a forwarded dead link, which is the exact case seven-day expiry exists for. A few extra rows per reader is the cheaper side of that trade.
  • Field defaults must be module-level functions. V1 lost a whole ticket to using shortuuid.uuid directly: it is a bound method on a module singleton, so every insert broke at runtime and Django's autodetector then looped, proposing the same migration forever.
  • Upload paths carry a UUID. Without it, re-uploading a corrected chapter either overwrites silently — leaving readers with a cached copy of the old file — or picks up a mangled storage suffix.
  • sent means the provider accepted it, not that it arrived. The column name is the shortest honest one available; the help text carries the rest.
  • A grant's __str__ never includes the token. D22 forbids putting a token anywhere it might be logged, and __str__ ends up in logs, admin and tracebacks.
  • Order.state does not exist. D64 derives it from the order's grants rather than storing it, so there is no second copy to fall out of step.
  • Ten tables, one file. Justified while it is ten; models.py is already 604 lines, and D59 has the move to per-domain apps waiting when it earns its keep.
