Why it exists

The companion is a discussion partner for one chapter, and the thing that makes it unusual is what it is not: not a tutor, not a quiz, not a summariser. It asks you questions — that is exploratory rather than evaluative (D13) — and it never interrupts (D14). It is silent until the reader opens it, and once opened it speaks first, with a question.

There is no retrieval and no chunking. The whole chapter goes into the system prompt, which is a cost decision as much as a quality one: input dominates, so prompt caching with a one-hour TTL is the lever that matters rather than an optimisation. Gaps between a reader's questions routinely exceed the default five minutes.

From a tap to an answer

What each part does

01
core/services/extraction.py
PDF → text_content and page_count, called explicitly from the admin save, seed_dev and the upload path — never from a signal. A file it cannot parse returns ok=False rather than raising: a chapter with no extracted text still reads perfectly, and only the companion is diminished.
02
core/content/companion_prompt.md · companion_opening.md
The prompt and the opening cue as content files, editable without touching logic — the same rule as labels.ts. The prompt carries {chapter_title} and {chapter_text} placeholders.
03
core/services/companion.py · system_prompt
Fills the template with the chapter's title and full text. No retrieval, no chunking — which is what makes input dominate and caching the thing that matters.
04
core/services/companion.py · check_caps
Every reason to refuse, before spending anything: the message is too long, this grant has had its messages for today, or the whole day's global ceiling is reached. Returns a Refusal code — it does not know what a 429 is.
05
core/services/companion.py · conversation
Turns the panel's thread into provider messages, keeping the most recent within a turn cap and a character budget. When the kept thread starts with the companion — which spoke first — the opening cue is put in front of it, because providers want the first message to be the reader's and that cue is what the companion was answering.
06
core/services/companion.py · _complete · _anthropic · _gemini
The only vendor-aware code in the repo, selected by the model name in env. Claude is the intended production provider; Gemini runs during the testing phase (D46). Swapping providers is this function body, because nothing above it knows a vendor type.
07
core/services/companion.py · record_usage
One ChatUsage row per grant per day, incremented with F() expressions. Two messages arriving together would otherwise each read the same count and write the same value — and a cap that undercounts is not a cap.
08
core/api/chat.py
Checks expiry, re-checks ownership, refuses plainly when the chapter has no extracted text, chooses between the opening cue and a real question, and maps refusal codes to 422 and 429. It owns no caps and no prompt.
09
components/Companion/machine/
closed → opening → idle → asking, with openingFailed, error and paused. Re-opening an existing conversation goes straight to idle; paused covers the cap, an unavailable provider and a chapter that is not ready.
10
components/Companion/index.tsx
A quiet launcher, then a side panel on a wide screen or a sheet on a phone (D88). It holds the thread in its own context and sends it with each turn — there is no server-side transcript.

The caps, and the cost model

SettingGuards against
COMPANION_MAX_INPUT_CHARSA pasted essay as a "question".
COMPANION_DAILY_MESSAGES_PER_GRANTOne reader on one chapter for a whole afternoon.
COMPANION_DAILY_MESSAGES_GLOBALThe bill, on a day when many readers arrive at once.
COMPANION_HISTORY_TURNS / _CHARSA thread that grows until every turn costs more than the last.
COMPANION_CACHE_TTLRe-sending the whole chapter at full price on every question. One hour, not the five-minute default.
COMPANION_MODELA hardcoded vendor. The name decides which client is used.

Gotchas

  • There is no console fallback. Every other external has one; this one refuses. A fake companion is worse than an absent one, because the reader would believe they had talked to something.
  • The token travels in the body, not the path. The panel is open inside a page that already has it, and a POST body reaches neither a referrer header nor an access log — the same reason the token is kept out of query strings. GrantAuth resolves it in both places so there is still one lookup.
  • A capped-out companion is a normal state. It renders as paused with the reason, not as an error — the reader did nothing wrong, and an error screen would suggest otherwise.
  • Read-modify-write would break the cap. Two simultaneous messages each read the same count and write the same value, losing one, which is why the increments are F().
  • A chapter with no extracted text is refused plainly. Letting the model improvise about a chapter it cannot see is the worst available outcome, so it answers 409 instead.
  • No transcript is stored. ChatUsage holds counts and never content, deliberately — but it also means a conversation cannot be resumed on a second device, and the owner cannot see what the companion said. That is a structural question rather than a bug, and it should be settled before the prompt is finalised.
  • The voice is still missing. The plumbing is finished and tested; the prompt itself, the way it opens with a question and how it declines an off-topic turn, is deferred to its own session. Until then the companion works and does not yet sound like anything.
