Why it exists

One line in CLAUDE.md shapes this whole feature: anything a human can do in Django admin, a service function does. The consequence is that every operation has at least two front doors — a screen and a command — and both go through the same service, so they produce the same rows and obey the same rules.

It also decides what operations are not: there is no queue, no broker and no worker (D17). Retry happens inside the request, the schedule is a cron job running a management command, and logs go to stdout for the host's own viewer with no log vendor (D22).

Two hands on the same services

What each command does

01
manage.py seed_dev
A demoable dataset from nothing, in one command, and idempotent — run it twice and the second run changes nothing, because it is the fastest way back to a working state and nobody should have to wonder whether it is safe. It goes through create_reader rather than writing rows: a seed that takes a shortcut stops proving the thing you wanted it to prove.
02
manage.py send_chapter --email … --chapter N [--dry-run]
The concierge's other hand: everything the admin resend action does, without a browser — which matters when the person fixing a failed delivery is already in a terminal. Through the seams, in order: can_read, mint_or_reuse, send_chapter.
03
manage.py cadence_tick [--dry-run]
What the cron runs every fifteen minutes. A trigger and nothing more, and its dry run lists due grants by primary key, reader and chapter — never a token or a link. Exits non-zero when a send failed so the run shows red.
04
manage.py render_chapters [--force]
Renders the pages of chapters that have none, so a chapter uploaded before server-side rendering existed becomes readable. It sits in the deploy start command because a chapter with no page images cannot be opened at all; after the first run it is one query per start.
05
manage.py machine_diagram
Every machine as a Mermaid state diagram, generated from its transition table, so the picture cannot drift from the code. No dependency beyond the tables themselves.
06
manage.py create_test_reader
A temporary command that makes an admin and a test reader on a chosen pace, for exercising cadence end to end. Its own docstring says to delete the file when testing is done — and it is still here.
07
core/admin.py
The eight model screens and the resend action, at /django-admin. Operations stay in core/services/* rather than accumulating inside admin classes, which is the constraint that keeps the in-app admin and this one honest about each other.
08
config/logging.py
One handler, stdout, at LOG_LEVEL. The host's log viewer is the log tool, and the transitions library's logger is pinned to ERROR so ignored triggers — normal, by design — are not noise.
09
AccountChange · MessageLog · ChatUsage
The three tables that are the audit trail: who changed an account, what we tried to send and what happened, and what the companion cost. In the spirit of D63 — every state change leaves a row.

The deploy runbook, in three lines

WhereRuns
buildpip install -r requirements.txt && manage.py collectstatic --no-input
startmanage.py migrate && manage.py render_chapters && gunicorn config.wsgi:application
cronmanage.py cadence_tick, every fifteen minutes

Migrations live in the start command rather than a pre-deploy hook because pre-deploy is a paid feature. The trade is that they re-run on every restart, including every wake from sleep — safe, because migrations are idempotent and the free tier is a single instance, so two cannot race.

Gotchas

  • A non-idempotent seed is worse than no seed. The whole value is being able to run it without thinking, so every object it creates is looked up before it is made.
  • A dry run must not print a token. The temptation is to show the link so you can click it; a token in a terminal ends up in scrollback, in a paste, and in a screenshot.
  • --stdout is not a safe flag name. Django's BaseCommand already owns self.stdout, and argparse would overwrite it with a boolean.
  • Refusals are not failures. cadence_tick counts them separately and exits zero: a deactivated reader or a row another tick was holding is the system working.
  • Two admins mean two ways to change one thing. Only the in-app admin writes an AccountChange row, so an edit made in Django admin leaves no trail.
  • There is no error tracker. Sentry is deferred by decision, and the revisit condition is explicit: before the first non-owner user. A failed delivery or a broken render is currently a log line nobody is watching.
  • create_test_reader is still in the repo. Along with ONBOARDING_ALLOW_PHONE_REUSE, it belongs to the list of things that must be gone before a real reader arrives.
